# Переход на события

## Проблемы и риски при росте нагрузки

1. **Получение каталога зависит от внешних API.** Сейчас агрегатор опрашивает все страховые компании в рамках одного запроса. После подключения ещё пяти компаний число внешних вызовов на обновление вырастет с пяти до десяти. Медленные ответы задержат обновление; без обработки частичных результатов ошибка одного API может сорвать его целиком.
2. **Локальные копии устаревают.** `core-app` обновляет каталог раз в 15 минут, `ins-comp-settlement` — раз в сутки. При сбое копия остаётся прежней до следующего успешного обновления. В результате сервисы могут использовать разные версии тарифа.
3. **Периодические выгрузки создают пики нагрузки.** Если обновления совпадут по времени, агрегатор повторно запросит одни и те же данные у страховщиков. Рост числа компаний увеличит нагрузку на внешние API и число одновременно занятых соединений.
4. **Ночной сбор реестра зависит от `core-app`.** Чем больше оформленных полисов, тем тяжелее суточная REST-выгрузка. При частичном ответе или повторном запуске нужны правила, исключающие пропуск полиса и двойной учёт; в исходном описании их нет.

## Предлагаемое взаимодействие

`ins-product-aggregator` продолжает получать и нормализовать продукты и тарифы. Он опрашивает страховщиков по расписанию, сохраняет изменения и публикует `ProductCatalogUpserted` и `TariffUpdated` в Kafka, в топик `insurance.product-catalog.v1`. `core-app` и `ins-comp-settlement` читают его в разных группах потребителей и обновляют свои локальные копии каталога. Периодические REST-запросы к агрегатору больше не нужны.

При оформлении полиса `core-app` публикует `PolicyIssued` в `insurance.policy.v1`. `ins-comp-settlement` добавляет полис в свой реестр по мере поступления событий. Это заменяет суточную выгрузку из `core-app`. Взаиморасчёты со страховыми компаниями остаются ежемесячными, как в условии задания.

Обязанности сервисов сохраняются. Web и партнёры обращаются к `core-app` по REST; данные клиента он получает из `client-info`. Сбой API страховщика задержит обновление каталога, но не помешает читать уже сохранённую копию. Перед оформлением необходимо проверять актуальность выбранного предложения: поток событий не устраняет задержку между изменением тарифа и обновлением копии.

## Зачем нужен Transactional Outbox

Если сначала записать полис в БД, а затем отправить событие в Kafka, сбой между этими действиями оставит полис без записи в реестре взаиморасчётов. Поэтому `core-app` сохраняет полис и запись в таблице `outbox` одной транзакцией. Агрегатор так же сохраняет изменение каталога вместе с событием.

Публикатор в составе сервиса читает outbox и отправляет события в Kafka. Запись помечается отправленной после подтверждения брокера. Если публикатор завершится после отправки, но до этой отметки, событие придёт повторно. Получатель сохраняет `event_id` и изменение своей БД одной транзакцией; повторный `event_id` пропускает.

События каталога имеют ключ `insurerId:productId`, события полисов — `policyId`. Публикатор сохраняет порядок изменений одного ключа. Получатели дополнительно проверяют версию записи, чтобы запоздалое событие или повторная обработка после ошибки не затёрли более новые данные. Одного `upsert` для этого недостаточно.

## Что потребуется при внедрении

- Отдельная группа потребителей для каждого сервиса, чтобы обновления каталога получали оба сервиса.
- Повторные попытки обработки; после исчерпания попыток — очередь ошибок (DLQ), уведомление и возможность повторной обработки.
- Контроль задержки потребителей, возраста неотправленных outbox-записей и времени последнего успешного обновления у каждого страховщика.
- Совместимые версии событий. В `PolicyIssued` передаются данные для взаиморасчётов, без копирования паспортных данных клиента.

Для перехода сначала включаем публикацию событий и строим новые локальные копии из согласованного снимка и последующих событий. Сверяем их с действующими данными. После сверки переключаем чтение на новые копии и отключаем REST-синхронизацию. Старый и новый механизмы до переключения пишут в разные копии, поэтому не перезаписывают результаты друг друга.
